# R41 压力测试计划 —— 多端并发负载验证

> 目标：验证线上打分系统在真实赛事峰值规模下的服务质量：
> **13+ 裁判同时评分、300 选手/观众并发访问、并发数 >20，且覆盖浏览器级真实访问**（不只后端 API）。

## 1. 被测系统

- 测试服务器：`http://59.110.90.21:8321`（阿里云单实例 uvicorn + SQLite WAL + SSE）
- 版本：R40 修复版（HEAD 4a5b0d1 之后）
- 数据：压测数据集（见 §2），与日常数据共存；压测后清理压测赛事

## 2. 压测数据集（tools/build_load_data.py，API 驱动写入测试服务器）

| 项 | 规模 | 说明 |
|----|------|------|
| 赛事 | 1 个「压测公开赛」 | 压测结束删除 |
| 选手 | 300（含 12 单位） | CSV 导入接口批量写入 |
| 裁判 | **13**（J1~J13） | 超过 9 的常规配置 |
| 场次 | 6+ | 大评分场 S1（300 人分组 3×100，评分制）、顺位大场 W1（48 人分组 4×12）、Mark 场 L1（32 人）、快速场 F1（8 人决赛，评分制，供并发提交压测） |
| 检录 | F1/W1/S1 全检录 | 开场状态 scoring |

## 3. 场景矩阵（tools/load_test_api.py 后端 + tools/load_test_browser.py 浏览器）

## 4. 梯度与安全

- 爬坡：每档稳定 60~90s；档间间隔 30s 观察恢复
- 熔断：连续 10s 错误率 >30% 或服务器 5xx 即中止该档（脚本内置）
- 压测机资源：浏览器并发 context ≤12，避免压测机自身成为瓶颈（压测机 CPU>85% 时数据标记无效）

## 5. 指标与判定标准

| 指标 | 合格线 |
|------|--------|
| API 错误率（非 429 防爆破） | < 1% |
| P95 响应时间（读接口） | < 1500ms（公网跨网基准） |
| P95 响应时间（写接口：评分/检录） | < 2500ms |
| SSE 建立成功率 | 100%，事件端到端延迟 < 3s |
| 浏览器 DOMContentLoaded P95 | < 5s（公网） |
| console error | 0（资源 404 除外） |
| 压测后服务器存活 | 服务 active、日常功能冒烟通过 |

## 7. 压测结果（2026-09-10 实测，公网 59.110.90.21:8321）

### 7.1 浏览器行为模拟 · 300 观众峰值（ramp 15/s，驻留 120s）

| 指标 | 结果 | 判定 |
|------|------|------|
| 错误 | **0** / 300 访客 | ✅ |
| HTML 完整时延 | P50 **56ms** / P95 4.5s* / avg 637ms | ✅ P50 优；*尾部见 §7.4 |
| 静态资源首访级联 | P50 1.3s / P95 7.5s* | *突发首访见 §7.4 |
| SSE 建立（工作人员端语义） | 300/300 | ✅ |
| 服务器负载（全程 uptime 采样） | **load 0.02~0.10（近空载）** | ✅ 远低于容量 |

### 7.2 后端 API 场景

| 场景 | 并发 | 请求数 | 错误 | P50 | P95 | 判定 |
|------|------|--------|------|-----|-----|------|
| B 13 裁判并发提交评分（90s） | 13 | 559 | **0** | 93ms | **112~141ms** | ✅ SQLite 写锁无竞争 |
| C 检录风暴·批量 12 人 toggle（90s） | 20 | 1340 | **0** | 34ms | **~125ms** | ✅ 14.8 RPS 持续写 |
| D 混合峰值（50 读+13 写+20 检录=83 并发，120s） | 83 | 6000+ | **0** | 读 67ms/写 89ms | 读 ~103ms/写 **137~188ms** | ✅ |
| E SSE 长连接 ×200 路（60s） | 200 | 200 | **0** | 首事件 0.25~0.46s | — | ✅ 建立率 100%，延迟 <<3s |

读接口基线（A 场景 100 VU 累计）：0 错误，P50 67ms，P95 ~103ms @ 31.8 RPS。

### 7.3 压测驱动的架构与性能优化（本轮落地）

1. **观众端去 SSE**（用户定案）：SSE 长连接仅保留工作人员端（裁判/检录/主持/管理员/大屏）；
   观众页**完全无后台自动请求**——只在打开页面或观众手动刷新时请求。
2. **公开页指纹 ETag 条件请求**：指纹（发布门数+场次指纹）在渲染前计算，无新内容时手动刷新
   直接 304（跳过渲染与传输）；本地实测 200→304。
3. **公开页渲染缓存**：同指纹并发只渲染一次（`_PUBLIC_PAGE_CACHE`），直解单 worker 下
   300 观众突发期 Jinja 渲染排队（HTML P95 5s 的 CPU 瓶颈）。
4. **静态资源 Cache-Control max-age=86400**（引用带 ?v= 版本参数，长缓存安全）：
   softReload 周期的重复资源请求 8510 → 0。
5. 公开页启用 HEAD 方法（此前 HEAD 405，健康检查/监控不可用）。

### 7.4 瓶颈分析与边界结论

- **服务端不是瓶颈**：300 观众峰值全程服务器 load < 0.1；单请求服务器本地处理 2~4ms
  （含渲染缓存后）；B/C/D 写场景跨网 P95 也仅 120~190ms。
- **P95 尾部来自公网路径**：本机→服务器 RTT 抖动 9~63ms（stddev 21ms），300 并发连接突发时
  压测端宽带上行/下行拥塞放大尾延迟（HTML P95 4.5s、突发首访级联 P95 7.5s）。
  真实赛事观众为分散入场，20 秒内 300 个新访客的突发是压测放大的极端假设。
- **判定**：并发 83（50 读+13 写+20 检录）全绿、SSE 200 路全绿、300 观众浏览器模拟错误 0、
  服务器近空载——**当前架构满足 13 裁判/300 选手观众/并发 >20 的目标，且有数倍余量**。

### 7.5 复跑方式

```bash

python3 webapp/tools/load_test_browser.py --vus 300 --duration 120 --ramp 15
# API 场景
python3 webapp/tools/load_test_api.py --scenario A --vus 100 --duration 90
python3 webapp/tools/load_test_api.py --scenario B --duration 90
python3 webapp/tools/load_test_api.py --scenario C --vus 20 --duration 90
DSPORT_MARSHAL_PASSWORD=.. python3 webapp/tools/load_test_api.py --scenario D --duration 120
python3 webapp/tools/load_test_api.py --scenario E --sse 200 --duration 60
```
